PROBLEM
  Loading 8.8M NPI provider records into MongoDB took 88.9 minutes.
  That is approximately 6× slower than the target SLA. The bottleneck
  was not hardware saturation — the same workload ran at 460 rows/s
  per worker in isolation but degraded to 170 rows/s under concurrency.
  The cause was write contention from an upsert pattern that performs a
  read-before-write on a live unique index, multiplied across 8–12
  concurrent workers hitting the same B-tree pages simultaneously.

ENVIRONMENT
  Platform        : Azure Durable Functions (Python 3.12, East US 2)
  Orchestration   : Fan-out/fan-in — orchestrator dispatches all 32 worker
                    activity functions simultaneously; Azure queues and
                    schedules them subject to Function App concurrency limits
  Workers         : 32 ProviderWorker instances
  Records/worker  : ~277,000 (NPI CSV partitioned by byte range)
  Batch size      : 5,000 rows per bulk_write call
  Write pattern   : UpdateOne($setOnInsert) upsert on (load_id, record_id)
  Index active    : (load_id, record_id) unique — maintained DURING load
  during load       Secondary indexes (zip, county.fips, worker_id) created
                    AFTER load completes
  MongoDB         : Atlas M30 (8GB RAM, ~4GB WiredTiger cache),
                    autoscale to M200
  Collection      : PublicHealthData.providers_staging (drained before load)

ANALYSIS
  The orchestrator dispatched all 32 workers simultaneously, but the
  Azure Function App's concurrency ceiling held execution to ~8 workers
  at a time. This produced distinct waves — not by design, but as a
  platform scheduling artifact.

  Workers running in 8-way concurrency averaged 170 rows/s. Workers
  running in near-isolation averaged 460 rows/s — a 2.7× gap at the
  same collection size. Critically, the LAST 4 workers ran against a
  fully loaded 8.8M-record collection and were the fastest (460–502
  rows/s). This rules out index size, collection growth, or WiredTiger
  cache pressure as root causes.

  The cause is write contention on the (load_id, record_id) unique index:
  - UpdateOne($setOnInsert) issues an index lookup (read) before every
    insert, even when the document is guaranteed not to exist (staging
    collection is drained before load starts).
  - Under 8-way concurrency, multiple workers compete for overlapping
    B-tree leaf pages, causing WiredTiger lock contention.
  - The read-before-write overhead scales linearly with concurrency;
    pure insert does not.

  The concurrency ceiling (8 simultaneous workers) also means the
  fan-out never runs at full 32-worker throughput. At 460 rows/s per
  worker × 32 workers the projected duration is 10 minutes.

IMPLEMENTATION — OPTIMIZATIONS APPLIED (commit 5dcb84d, 2026-03-23)
  1. InsertOne replacing UpdateOne($setOnInsert)
     - Eliminates read-before-write on every row
     - staging collection is drained before load, so no prior document
       exists; pure insert is safe
     - Duplicate key errors on retry remain the safety net

  2. (load_id, record_id) unique index deferred to post-load
     - Index previously maintained incrementally per insert —
       every batch triggered B-tree rebalancing
     - Index now created once over the complete dataset after all
       workers finish, matching the pattern of the other 3 indexes
     - ensure_preload_indexes_fn made a no-op; index moved to
       ensure_postload_indexes_fn

  3. Azure Function App concurrency ceiling raised
     - host.json: maxConcurrentActivityFunctions = 32
       (was effectively ~8; platform default)
     - Allows all 32 workers to execute simultaneously
     - Only fully effective combined with #1 and #2 above

  4. Batch size increased 5,000 → 10,000
     - Halves the number of round-trips to MongoDB per worker
     - Larger batches amortize per-call network overhead

  5. MongoClient maxPoolSize raised to 64
     - Was unbounded; Azure Functions can create many short-lived
       connections per worker under load
     - Pool cap prevents connection exhaustion under peak fan-out

SLA CONTEXT

                                       at observed isolation throughput)
  Actual performance requires measurement on the optimized run.
