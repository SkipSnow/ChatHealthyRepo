ANALYSIS
  The orchestrator dispatched all 32 workers simultaneously but the Azure
  Function App executed them in waves of ~8, limited by its concurrency
  ceiling. This staggering is NOT by design — it is a platform scheduling
  artifact.

  Workers in the same wave ran concurrently against the same MongoDB
  collection and index. Write throughput per worker degraded 3x under
  8-way concurrency (~170 rows/s) vs near-isolation (~460 rows/s).

  Critically: the last 4 workers ran against a FULLY LOADED collection
  (8.8M records already present) and were the FASTEST. This rules out
  index size or collection growth as the cause. The bottleneck is
  concurrent write contention on the (load_id, record_id) unique index —
  multiple workers competing for the same B-tree pages simultaneously.

  The $setOnInsert upsert pattern requires a read (index lookup) before
  every write. Under high concurrency this creates lock contention on
  WiredTiger index pages even when all writes target different documents.

RECOMMENDATIONS FOR GPT REVIEW
  1. Replace upsert with insertMany (ordered=False)
     - drain_staging guarantees an empty collection before load starts
     - Remove the read-before-write; pure inserts have lower contention
     - Handle duplicate key exceptions as a safety net for retries

  2. Move (load_id, record_id) index creation to AFTER load completes
     - Currently the unique index is maintained incrementally per insert
     - Building it once over existing data is significantly faster
     - Secondary indexes (zip, county.fips, worker_id) already do this

  3. Tune Azure Function App concurrency ceiling
     - Current ceiling appears to be 8 concurrent executions
     - Raising this (host.json maxConcurrentActivityFunctions) would
       allow more workers to run simultaneously — but only helps if
       MongoDB contention is resolved first

  Question for GPT: given these constraints, what concurrency level and
  batch size would you target to achieve a 15-minute load SLA?
